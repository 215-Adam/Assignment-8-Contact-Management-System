Design Memo: Contact Hash Table

A hash table is the right structure for fast lookups because it turns a key directly into a location. Rather than scanning every contact, my hash_function adds up the ord() value of each character in a name and takes the remainder when divided by the table size. That produces an array index, and because arrays give constant-time access by index, search and insert both run in O(1) time on average, no matter how many contacts are stored.

Collisions are unavoidable, since many names can map to a limited number of slots. "Amy" and "May" show this clearly: as anagrams, they have identical character sums and always land at the same index. I handled this with separate chaining, where each array slot holds the head of a linked list of Node objects. On insert, I walk the list at the hashed index. If the name already exists, I update that contact's number, which prevents duplicates. Otherwise, I append a new node to the end. Search follows the same path and compares full names, so colliding contacts stay distinguishable. In the worst case, when every key lands in one slot, operations degrade to O(n), so a good hash function and an adequately sized table matter.

An engineer might choose a hash table over a list when most operations are lookups by exact key, since a list requires O(n) scanning. Directories, caches, and database indexes are typical examples. A tree is the better choice when data must stay sorted or support range queries, such as finding every name between "A" and "C", because hash tables deliberately scatter keys and keep no meaningful order. Trees also guarantee O(log n) performance when balanced.
